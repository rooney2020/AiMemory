# feedback 长时挂机观察说明

## 目标

在用户长时间挂机、feedback 窗口保持开启并自动回复的情况下，完整记录 feedback 调用链路，判定断开的真实原因。

## 观察原则

- 同一时刻只允许一个活跃 feedback。
- 在旧 feedback 返回前，禁止再次发起新的 feedback。
- 如果用户已经在聊天里直接回复，则立刻放弃等待旧 feedback，不再把旧 feedback 视为活跃。
- 如果用户主动结束会话，返回 `Canceled`，应判定为用户手动结束，不应误报为连接异常。

## 必须记录的时间点

### AI 侧时间

- T1：AI 发起 feedback 的时间
- T2：AI 收到工具返回结果的时间
- T3：AI 检测到异常并做出判定的时间

### 用户侧时间

- U1：用户看到 feedback 窗口的时间
- U2：用户自动回复或手动回复的时间
- U3：用户手动结束窗口的时间（如果发生）

## 需要记录的结果字段

- `tab_id`
- `tab_title`
- 返回结果原文
- 是否出现 `Canceled`
- 是否出现 `Connection closed`
- 是否出现 `Tool not found`
- 是否出现超时/心跳提示
- 当前是否存在第二个 feedback 被错误发起

## 断开原因判定表

| 现象 | 判定 | 说明 |
|---|---|---|
| 返回 `Canceled`，且用户确认手动结束 | 用户主动结束 | 不是连接问题，也不是超时 |
| 返回 `Connection closed` | 连接中断 | 倾向于 Cursor/MCP 连接层问题 |
| 长时间无结果，随后出现心跳或超时重连 | 超时/保活链路 | 需要记录超时时长 |
| 用户已回复，但 AI 仍卡在旧调用 | 代理状态管理错误 | 多为重复发起 feedback 或未清空旧等待 |
| 同轮出现两个 feedback 窗口 | 重复调用错误 | 必须检查是否同一 `tab_id` 被替换 |

## 本轮重点排查

- 观察挂机时 feedback 是否自然返回。
- 如果断开，先看是不是用户主动结束。
- 如果不是，再看是否有 `Connection closed` 或类似连接错误。
- 如果也没有，再核对是否超时。
- 如果用户已回复但 AI 还在等待，优先判定为代理状态管理错误。

## 预期输出

最终要形成一条完整链路：

1. feedback 何时发起
2. 用户何时收到并回复
3. 工具何时返回
4. 返回了什么
5. 为什么断开
6. 责任更接近用户主动结束、连接层、超时机制，还是 feedback 调用管理错误
