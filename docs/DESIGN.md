# AI Memory 设计总览

> 本文档用于描述当前实现的核心设计。早期未落地或已废弃的桥接式方案已经移除，避免与现有代码结构混淆。

---

## 一、设计目标

1. 本地优先：核心数据存放在 SQLite，本地即可完成读写和检索。
2. CLI 优先：把稳定能力收敛到命令行入口，方便不同 AI 助手统一接入。
3. 人类可读：除数据库外，保留可读层与索引，便于排查和降级浏览。
4. 多助手复用：同一套记忆规则可被 Cursor、Copilot 与其他 Agent 复用。
5. 图谱增强：通过 `entities`、关系表与重建流程提高知识聚合能力。

---

## 二、总体架构

```text
用户 / AI 助手
        │
        ├─ rules / instructions / skills
        │
        ├─ backend/cli.py
        │
        ├─ SQLite 数据库
        │   ├─ memories
        │   ├─ entities
        │   ├─ relations
        │   └─ assets
        │
        ├─ readable/ + INDEX.json
        │
        └─ qt-frontend/
```

核心思路是把“命令入口、存储层、图谱层、可读层、前端层”分开，让任何助手都能先通过 CLI 使用同一套底层能力。

---

## 三、记忆模型

系统保留三类核心记忆：

| 类型 | 用途 | 常见内容 |
|---|---|---|
| episodic | 记录阶段性事件与结果 | 修复过程、验证结果、会话摘要 |
| semantic | 沉淀可复用知识 | 架构结论、根因分析、规则说明 |
| procedural | 固化长期规则与偏好 | 用户偏好、工作流要求、禁用项 |

每条记忆建议尽量带上：

- `summary`
- `content`
- `project`
- `entities`
- `tags`

其中 `entities` 是图谱层的重要输入，而不是可有可无的装饰字段。

---

## 四、检索设计

当前检索链路以融合检索为核心，常见维度包括：

- 全文：适合命中明确关键词
- 图谱：适合按实体或关系追溯相关记忆
- 时间：适合近期活动和阶段追踪
- 可选语义能力：在环境支持时增强相近表达召回

最终目标不是展示某一种索引，而是让 `recall` 在当前实现约束下给出稳定、可解释的结果。

---

## 五、图谱设计

图谱层围绕实体与关系展开：

- 记忆中的 `entities` 会同步到实体关联层
- 多实体共现可形成关系候选
- 老记忆补齐实体后，可以通过 `rebuild-graph` 重建关系

设计原则：

1. 优先保证实体命名稳定。
2. 优先抽取项目、模块、组件、工具、框架、关键问题名。
3. 大批量补实体后再做图谱重建，避免频繁全量刷新。

---

## 六、资产设计

资产层用于沉淀可复用成果物，例如：

- 自己写的脚本
- 已下载并验证过的工具
- 报告、原型、数据产物
- 可重复使用的测试应用或配置文件

设计重点：

1. 资产必须带可追踪路径。
2. 资产默认区分有效与失效状态。
3. 资产应能通过项目、标签、关键词复用。
4. 资产复用行为应反馈回工作流，而不是只做静态登记。

---

## 七、前端与规则层

Qt 前端负责可视化浏览和管理；规则文档负责告诉 AI 何时检索、何时记忆、何时注册资产。二者共享同一套数据库与底层约束。

当前推荐分工：

- 文档规则：约束 AI 行为
- CLI：提供稳定执行入口
- Qt 前端：负责人工浏览、核查和管理
